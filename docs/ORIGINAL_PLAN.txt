# MerkleLSM: Team Guide
*A tamper-evident audit ledger built on an LSM Tree, in Rust. One week, four people.*
---
## 1. What are we building? (the 30-second version)
We are building a **mini database** that:
1. Saves data **very fast** (that is what an LSM Tree is good at).
2. Survives **crashes** without losing data.
3. Can **prove nobody secretly edited** the saved data (that is the Merkle tree part).
Real-world use: bank or audit records, where "was this changed later?" matters as much as saving the data.
**Our data structure for the project sheet:** LSM Tree.
Supporting pieces: skip list, Bloom filter, Merkle tree.
---
## 2. The analogy: a busy accountant's office
Imagine an accountant who receives hundreds of receipts a day.
| In the office | In our project | What it does |
|---|---|---|
| The **diary** where every receipt is written down first, in order | **WAL** (write-ahead log) | If the power goes out, the diary lets us rebuild what we lost |
| The **sticky-note pad** on the desk, kept sorted | **Memtable** (a skip list) | Fast place to put new data, held in memory |
| When the pad is full, the notes are filed into a **sorted folder** that is never edited again | **SSTable** (sorted string table) | Permanent, sorted, read-only file on disk |
| A quick glance at a folder's label: "this key is definitely NOT in here" | **Bloom filter** | Skips folders we don't need to open |
| Merging many small folders into one tidy folder | **Compaction** | Keeps reads fast and the folder count low |
| A **wax seal** on each folder, built from seals on each page | **Merkle tree / Merkle root** | If anyone changes even one page, the seal no longer matches |
| An inspector checking every seal | **`verify` command** | Finds exactly which folder and page was tampered with |
**The key idea:** writing is cheap because we only *add* to the pad and the diary. We never go back and edit old folders. Reading checks the pad first, then folders from newest to oldest.
---
## 3. How it works, step by step
**Writing (`put`)**
1. Write the record to the diary (WAL), so it survives a crash.
2. Put it on the sticky-note pad (memtable).
3. When the pad is full, file it as a new sorted folder (SSTable) and add a wax seal (Merkle root).
**Reading (`get`)**
1. Look on the pad.
2. If not found, check folders from newest to oldest. A Bloom filter skips folders that cannot have it.
3. The newest version of the key wins. A "deleted" marker (tombstone) means the key is gone.
**Checking (`verify`)**
1. Re-read every page of a folder and recompute its seal.
2. Compare with the seal stored when the folder was created.
3. Mismatch means tampering, and we report the exact folder and block.

## 4. Who does what
Fill in names: **A = ______, B = ______, C = ______, D = ______**
### Person A: The Sticky-Note Pad and the Front Desk
**Owns:** `memtable/` and `db.rs`
- Build a **skip list** (store nodes in a `Vec` and link them by index, so no `unsafe` code)
- Support `insert`, `get`, ordered iteration, and a size counter so we know when it's "full"
- Write `db.rs`, which connects everything: `Db::open`, `put`, `get`, `delete`, `scan`, `flush`
- Handle sequence numbers (every write gets a bigger number than the last)
**Done when:** skip-list tests pass; `Db` can put and get across flushes.
**Learn first:** Rust ownership basics, `Vec`, `Option`, how a skip list works.
### Person B: The Diary and Crash Recovery
**Owns:** `wal/` and file handling
- Define the WAL record format: `[crc32][length][type][seq][key_len][key][value_len][value]`
- Append records and call `sync_all()` for durability
- On startup, **replay** the WAL into the memtable; stop cleanly at a half-written record (bad CRC or short read)
- Handle WAL rotation after a flush, and keep track of SSTable file names and numbering
- Write the **crash test**: truncate the WAL at random points, reopen, and check nothing complete is lost
**Done when:** killing the program mid-write and restarting recovers all complete records.
**Learn first:** `std::fs`, `BufWriter`, the `crc32fast` crate.
### Person C: The Folders (SSTables)
**Owns:** `sstable/` and `bloom.rs`
- **Builder:** write sorted entries into ~4 KB blocks, then an index block, then a footer
- **Reader:** open a file, binary-search the index, read one block, return the entry
- **Iterator:** walk an SSTable in order (needed for scans and compaction)
- Hand each block's bytes to Person D's `hash_block`, and store the leaf hashes and Merkle root in the file
- Stretch: Bloom filter per SSTable; simple compaction (merge all SSTables into one using a heap)
**Done when:** flush a memtable, restart, and read every key back from the file.
**Learn first:** binary file layouts, `BufReader`, `seek`, and byte encoding.
### Person D: The Wax Seals, the Inspector, and the Shop Window
**Owns:** `merkle/`, `main.rs` (CLI), CI, README, docs
- **Merkle:** `hash_block(bytes) -> [u8; 32]` using `sha2`; build a tree from leaf hashes; return the root; verify a tree
- **`verify` command:** recompute and compare roots, then report the exact file and block that failed
- **`tamper` demo command:** flip one byte in a chosen block, so we can show detection live
- Stretch: `prove <key>` (block hash plus sibling hashes up to the root)
- **CLI** with `clap`: `put`, `get`, `delete`, `scan`, `flush`, `compact`, `verify`, `stats`
- Set up GitHub, CI (fmt, clippy, test), README, and docs; keep the demo script up to date
**Done when:** corrupting one byte makes `verify` point to the exact block.
**Learn first:** how Merkle trees work, the `sha2` and `clap` crates.

## 8. Glossary
- **LSM Tree:** a storage design that buffers writes in memory and flushes them as sorted, immutable files, then merges those files over time.
- **WAL (write-ahead log):** an append-only file that records each write before it is applied, so crashes don't lose data.
- **Memtable:** the in-memory sorted structure that receives new writes.
- **SSTable:** an immutable, sorted file on disk.
- **Tombstone:** a marker meaning "this key was deleted".
- **Compaction:** merging SSTables to reduce file count and clean up old data.
- **Bloom filter:** a compact structure that says "definitely not present" or "maybe present".
- **Merkle tree:** a tree of hashes where each parent hashes its children; the top hash (root) changes if any leaf changes.
- **Merkle proof:** the small set of hashes that proves one block belongs to a given root.
- **Sequence number:** an ever-increasing counter that orders writes.
